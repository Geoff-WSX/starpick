# 生产级优化方案 · 可行性分析报告 v1.1 审查

> 版本：v1.0 ｜ 日期：2026-10-08 ｜ 审查对象：`可行性分析报告.md` v1.1
> 审查标准：生产级 checklist（健壮性 / 可观测性 / 安全 / 数据 / 性能 / 测试 / 工程化 / 调度可靠性 / 前端健壮性）
> 优先级：**P0 必须**（生产级底线）｜ P1 建议（明显增益）｜ P2 可选（按需演进）

---

## 1. 总体结论

v1.1 方案架构方向正确（三层解耦、技术选型成熟），达到"**能跑**"标准；距"**生产级**"尚有 9 项 P0 + 7 项 P1 缺口，集中在**容错、可观测、安全、测试**四块。补齐后即为可长期无人值守运行的本地生产服务，工作量预计增加 25%~35%。

---

## 2. P0 必须项（9 项，生产级底线）

| # | 维度 | 问题 | v1.1 现状 | 优化方案 |
|---|---|---|---|---|
| P0-1 | 调度可靠性 | **采集任务无防重入锁** | 未设计。若上一轮因网络慢未跑完，APScheduler 触发下一轮将并发执行两轮采集 | 单实例锁：`rounds` 表建"运行中"任务行（或进程文件锁）；触发时检测到运行中则跳过本轮并记日志 |
| P0-2 | 健壮性 | **失败重试未分级** | 仅笼统写"指数退避重试"，瞬时/持久错误不区分 | 分级处理：429 按 `Retry-After` 等待；5xx/超时指数退避（上限 N 次）；401/404 等持久错误立即失败不重试；整轮失败写入 rounds 状态并支持重跑 |
| P0-3 | 可观测性 | **无健康检查端点** | 未设计 | 新增 `GET /health`：DB 连通性、最近一轮状态、下一轮计划时间、服务版本；供自诊断与启动脚本检查 |
| P0-4 | 可观测性 | **日志无轮转、无结构化** | 基础 `logging` 单文件 | `RotatingFileHandler`（按大小轮转 + 保留份数）；关键事件输出单行结构化（时间/环节/事件/耗时/结果），失败日志含上下文便于排障 |
| P0-5 | 安全 | **Token 存在配置泄漏风险** | config.yaml 明文存 GITHUB_TOKEN，未来分享项目易泄漏 | Token 只从环境变量/本地 `.env` 读取（`.env` 不入库、不分享）；config 仅支持 `${GITHUB_TOKEN}` 引用；文档写清生成与配置步骤 |
| P0-6 | 安全 | **服务绑定范围未明确** | 未定义 | 默认绑定 `127.0.0.1` 仅本机访问；若开放局域网访问列入 P2（需鉴权） |
| P0-7 | 数据 | **无 schema 迁移机制** | 表结构演进无版本管理，改表易出错 | `schema_version` 表 + 顺序迁移脚本；启动时自动检测并执行迁移，迁移失败则拒绝启动并提示 |
| P0-8 | 质量 | **无测试策略** | 报告中未提及 | pytest 三层测试：① 纯函数单测（筛选打分、平台推断、系统要求提取、中文检测）② GitHub API mock 集成测（模拟正常/429/失败路径跑通一轮入库）③ API 契约测（FastAPI TestClient 验证各端点响应结构） |
| P0-9 | 工程化 | **依赖未锁定版本** | `requirements.txt` 未 pin | venv 隔离环境；主依赖精确锁版（`pip freeze`）；`requirements-dev.txt` 含 pytest 等测试依赖 |

## 3. P1 建议项（7 项，明显增益）

| # | 维度 | 问题 | v1.1 现状 | 优化方案 |
|---|---|---|---|---|
| P1-1 | 健壮性 | **进程崩溃不自愈** | 仅提供手动 start.bat | start.bat 内置"退出自动重启"循环（记录退出码与重启次数，连续崩溃 N 次停止并提示）；可选"登录时自动启动"任务计划 |
| P1-2 | 调度可靠性 | **休眠错过调度、时区未定** | 未设计 | APScheduler 显式配置 `Asia/Shanghai` 时区；`misfire_grace_time`（如 3600s）容忍短时错过；启动时判断"上次成功轮次距今超 2 个周期"则立即补跑一轮 |
| P1-3 | 性能 | **采集串行较慢** | 每轮约 60 次 HTTP 请求串行（≤5 分钟） | README/release 二次抓取用线程池并发（默认 6 并发，可配）；搜索请求仍串行排队以守住限流配额 |
| P1-4 | 数据 | **无保留策略** | 未设计 | rounds 保留最近 N 轮（默认 90，可配，超期归档/清理）；projects 按 `full_name` 去重更新而非重复插入 |
| P1-5 | 数据 | **去重策略单一** | "已推荐即永久跳过" | 可选增强（config 开关）：项目出现重大更新（star 翻倍 / 新 major release）时允许再次推荐，避免优质项目沉底 |
| P1-6 | 可观测性 | **失败无触达** | 失败只进日志 | rounds 状态在历史页高亮（失败轮次红色标记）；连续失败 N 轮时启动摘要/页面顶部显式提示；本地工具不引入外部通知服务（务实） |
| P1-7 | 工程化 | **配置启动不校验** | 未设计 | 启动时校验 config：分类非空、阈值范围合法、端口未占用、Token 格式合法；错误早失败并输出定位信息（第几项配置问题） |

## 4. P2 可选（4 项，按需演进，不影响本期交付）

| # | 维度 | 项 | 说明 |
|---|---|---|---|
| P2-1 | 性能 | 全文搜索 | 项目量达到数千后，将关键词搜索从 SQLite LIKE 迁移至 FTS5 全文索引 |
| P2-2 | 前端 | 大列表渲染 | 单分类卡片 > 100 时启用虚拟滚动 + 图片懒加载 |
| P2-3 | 工程化 | dev/prod 双模式文档化 | 明确两种运行模式：开发（vite dev + proxy + 热更新）vs 生产（build + FastAPI 静态托管），提供对应启动脚本 |
| P2-4 | 安全 | 局域网访问（含鉴权） | 本期仅本机；未来如要手机/平板访问，增加简单鉴权（访问令牌）与 `0.0.0.0` 开关 |

## 5. 对里程碑的调整建议

| 里程碑 | 在原 v1.1 基础上增加 |
|---|---|
| M1 后端 | 防重入锁、重试分级、`/health`、日志轮转、schema 迁移、config 启动校验、pytest 基础用例（筛选/提取/平台推断单测） |
| M2 前端 | 统一请求封装（加载态/错误提示+重试/空态）、下载链接 `rel="noopener"`、历史页失败轮次高亮、页面版本号 |
| M3 端到端试跑 | 验收增加：单测+契约测全部通过；故障演练（断网降级、429 限流、端口占用、重复触发防重入） |
| M4 交付定型 | 启动自愈脚本、`.env` 模板、README 增"故障排查"章节（Token 失效/端口占用/连续失败处理） |

## 6. 实施顺序建议

1. **先补 P0**：防重入锁 → 重试分级 → schema 迁移 → Token 环境化 → 绑定 127.0.0.1 → 日志轮转 → /health → config 校验 → pytest 骨架；
2. **再上 P1**：崩溃自愈 → 时区/misfire/补跑 → 并发抓取 → 保留策略 → 失败高亮 → dev/prod 文档；
3. **P2 留接口不实现**：设计时预留（如查询层抽象便于日后换 FTS5），不增加本期工作量。

**验收底线（生产级）**：连续运行 72 小时无人工干预；断网/429/端口冲突下服务不崩溃、下一轮自动恢复；任意时刻 `GET /health` 可判断服务健康；核心纯函数测试覆盖率 ≥ 80%。
